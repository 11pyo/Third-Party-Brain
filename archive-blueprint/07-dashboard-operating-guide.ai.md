# DASHBOARD — OPERATING RULES & USAGE

> 05-operational-layer = 개념/불변식(INV-OL1~4). 이 문서 = 운영 규칙(R1~R17) + 헬퍼 CLI 계약 + 렌더 시맨틱.

## BOARDS (3, in task-board.html)
- **프로젝트 태스크**: 상태 칸반 접수/진행중/대기/완료. cards = `const TASKS` (정본 미러).
- **정기업무**: 주/월/연 cadence 별보드(일회성과 분리, 평소 "트리거 대기").
- **문의이력**: 상태 칸반 4열, 데이터=`inquiry-log.js`(id-merge fold).
- 카드: id + title + **requester chip(req)** + due + next-action + detail(collapsible). 완료열 max-height+overflow, newest-first; **완료열 한정** `+전체보기`(완료 카드≥1)→모달(openFullView).
- TASKS 카드 스키마(프로젝트 태스크): `{id, cls(분류→색상클래스: 개발|운영|트러블 등), title, status:"접수"|"진행중"|"대기"|"완료", req(요청자·조직), due, next, detail, warn:bool}`. **정기업무 카드는 status 대신 반복주기(cadence: 주례|월례|연례)** 를 가져 정기 보드로 분리 렌더(평소 "트리거 대기"). ↔ 문의로그 FIELD SCHEMA는 아래 HELPER 절.

## HELPER CLI CONTRACT (log-inquiry.py)
```
① 접수:  --new --type 단순문의|일반요청|긴급문의 --q "<요약>" --by <기록자> --req "<요청자·조직>" [--date YYYY-MM-DD]
          → stdout 'NEW id=INQ-YYMMDD-HHMMSS' (id 보존 필수; --id 미지정 시 타임스탬프로 자동생성)
② 전이:  --id <id> --status 진행중|대기
③ 완료:  --done --id <id> --a "<처리/답변>" --ref "#<앵커>"   (=--status 완료)
※ 접수+즉답: ①에 --a 또는 --status 완료 동봉 → 바로 완료
```
- FIELD SCHEMA: `{id, date, type, q, a, by, req, ref, status:"접수"|"진행중"|"대기"|"완료"}`.
- APPEND 시맨틱: 매 호출 = `window.INQUIRY_LOG.push({...})` 1줄 추가. **빈 값 필드는 안 보냄**(준 값만 갱신).
- ID-MERGE: 같은 id 후속 push가 prior 필드 덮어쓰기 병합 → 상태전이=append(수정 아님). 렌더가 id별 fold.
- CONCURRENCY: append를 OS 파일락(`.lock` 게이트; Windows msvcrt.locking / POSIX fcntl.flock)으로 보호. 락 실패해도 기록 유지(best-effort). → 멀티 writer 충돌 0.
- ID-ALLOC(`--new`, 2026-09-10~): 자동 id 는 초 단위 시각이라 같은 초 두 건이 한 id 로 병합됐다 → **락을 쥔 채** 로그에서 이미 쓰인 id 인지 보고, 쓰였으면 1초씩 밀어 빈 번호를 쓴다(형식 `INQ-YYMMDD-HHMMSS` 불변 · stdout 의 id 가 실제 id). 실측: 같은 초 동시 4건 → id 4개 모두 다름·글 섞임 없음.
- VALIDATION: status는 4값만; `--id`만 주고 변경필드 없으면 거부; `--new`도 `--id`도 없으면 거부.

## RENDER SEMANTICS (task-board.html)
- `mergedTasks() = TASKS.map(t => ({...t, ...overrides[t.id]}))` — localStorage override 병합.
- 편집(openEdit)=localStorage override만(정본 불변). 정본 반영 = 💾 저장 **3단 폴백**: ①로컬 저장 서버(`board-saver.py` POST /save/board·/save/inquiry — 경로 안 물음) ②브라우저 File System Access(첫 1회 파일 선택 → 핸들을 IndexedDB에 보관, 앱별 키+파일명 검증) ③다운로드. 「변경분 내보내기(JSON)」는 레거시 수동 경로.
- 저장 시맨틱 2종: **보드**=렌더된 DOM 클론에서 `const TASKS` 배열만 현재값으로 치환해 **파일 전체 재작성**(치환 패턴 불일치 시 저장 중단 — 배열이 쪼개져 있으면 조용히 무효화되던 사고 방지). **문의로그**=바뀐 필드만 `push()` 줄 **append**(다세션 안전, 헬퍼 CLI와 동일 규약).
- 서버 저장 성공 시 변경분을 메모리(`TASKS`/`INQUIRY_LOG`)에도 반영 → 새로고침 없이 화면 상태 유지.
- 문의보드: INQUIRY_LOG를 id별 최종병합 → 상태별 컬럼 분배 → 완료열 scroll. 새로고침=반영(빌드 없음).

## OPERATING RULES (R1~R17)
- R1 정본=`tasks.md`(md), 화면=`task-board.html` 미러. 태스크 변경=둘 다 갱신(동기화는 작업의 일부).
- R2 `inquiry-log.js`는 헬퍼 전용(append-only+id-merge 무결성 — 직접편집 금지).
- R3 멀티세션 전권(파일 도메인 분리 없음; 빈 세션 1=프로젝트 1 완주). 충돌방지 2: ①편집 직전 재읽기 ②문의로그는 헬퍼만.
- R4 requester chip(req=요청자·조직) 채움 → 추적·라우팅.
- R5 태스크 추가/삭제 시 3곳 동기화: 정본 md / 화면 TASKS / 집계 카운트.
- R6 정기업무는 일회성과 분리·트리거 대기.
- R7 완료열 scroll·newest-first·전체보기 모달.
- R8 민감정보는 데이터파일(로컬)에만. 공개본=구조·규칙·익명예시만. PII(전화·이메일·사번) 데이터파일에도 미기록(비공유 로컬).
- R9 저장 서버는 **127.0.0.1 전용 쓰기 API**. LAN 공개(0.0.0.0) 금지 — 읽기 전용 아카이브 서버(`--share`)와 성격이 다르다. 커스텀 헤더 요구 + 형식·크기 검증 + 쓰기 전 백업이 최소 안전장치.
- R10 접수 서버(`intake-server.py`, 5179)는 **0.0.0.0(사내망 공개 — 의도)이지만 쓰기는 둘뿐이다**: `POST /api/new`(신규 등록) · `POST /api/followup`(본인 문의에 추가 질문, 문의당 최대 10회). 스크린샷은 **이 두 요청에 base64 로 함께 실려서만** 들어온다 — 따로 올리는 엔드포인트는 두지 않는다(글만 들어가고 그림이 빠지거나 번호가 어긋나는 일 방지). 상태·답변 수정·삭제 엔드포인트는 만들지 않는다. 서버 안의 쓰기(신규 등록·추가 질문·그림 정리)는 **쓰기 잠금 하나로 줄 세운다** — 같은 문의 동시 추가 질문의 사진 번호 겹침, 정리가 막 쓰는 그림을 지우는 경쟁을 막는다. 거절할 요청도 본문을 끝까지 읽고 답한다(연결 끊김 대신 진짜 거절 사유가 브라우저에 보이게). 저장 서버(5178, 127.0.0.1 쓰기 API)와 성격이 다르니 절대 합치지 말 것.
- R11 공개 노출 3중 제한: ①`by="웹접수"` 기록만 ②성함+소속 완전일치분만 ③`_public_view()` 화이트리스트 — id·date·type·status·q·a + turns(대화 턴)·followups·can_ask·shots(첨부 번호 목록)·shot_left(남은 사진 자리). `ref`·`by`·`req` 는 나가지 않는다. 그림(`GET /api/shot`)도 본인 확인 통과 시에만 준다. **담당자 대시보드(`task-board.html`)와 `inquiry-log.js` 원본은 서빙하지 않는다** — AI 참조 로그가 통째로 노출된다.

- R14 **부재중 모드(원표봇) — 에이전트는 쓰지 않는다.** 감시자(`vacation/watcher.py`)가 부르는 헤드리스 에이전트는 읽기 도구만(Read·Grep·Glob + 개발계 SAP 조회 6종) 갖고 판정 JSON(`answer|hold|escalate|dev` + public·note·ref)만 돌려준다 — 쓰기를 맡겼더니 명령 모양 차이로 권한 거부 → 조사만 하고 조용히 멈췄다. 기록은 **단일 쓰기 게이트**(`vacation/apply_answer.py`, `log-inquiry.py` 경유) 한 곳: ①표기 `[원표봇 · AI 1차 안내 · 담당자 부재중]` 강제 부착(뗄 수 없음 — 이름을 붙여도 AI 라는 사실은 지우지 않는다) · 정정 안내는 hold 에 붙이지 않고 escalate·hold 엔 팀장 안내 줄 · **note 는 답변에 붙이지 않는다**(journal 에만 → 복귀 보고서 「담당자용 메모」, 현업에게 가지 않음) ②상태는 **항상 「대기」**(완료로 닫는 건 사람) ③기록 후 **재조회로 반영 확인**(새로 쓴 턴만 공개 렌더 검증 — 축소율 검사가 대화 전체를 표준 문구로 덮어쓴 사고). 트리거는 **이벤트**(로그 변경 → 45초 디바운스, 무변경 시 600초 재조정) — 폴링으로 LLM 을 부르지 않으므로 **대기 중 비용 0**, 처음 보는 건은 LLM 없이 즉시 「접수 확인」(어떤 장애에도 침묵하지 않게) — 단 **답변란이 비어 있을 때만** 쓴다(아니면 생략 — 앞선 AI·보류 답을 통째로 덮어쓴 결함). **처리 대상 = 건별 상태**: 사람이 답한 건 = 영구 제외 · 완료 = 제외 · 「답했다」는 **물은 만큼 답했는가**(질문 턴 = 1 + 추가 질문 수 vs 답 턴 = ⏱ 줄 수, ⏱ 이전 옛 답은 「AI 1차 안내」 표기로 셈) — AI 가 답한 카드라도 미답변 추가 질문이 붙어 있으면 처리 대상 · 켤 때 담당자가 진행중·대기로 옮겨 둔(답 없는) 건은 가로채지 않는다(추가 질문이 붙으면 다시 잡힘). 켤 때 이 기준으로 `seen.json` 을 먼저 심어 켜기 전 미답변(접수 확인만 붙은 건 포함)을 backlog 로 곧바로 처리하고, 다 답한 카드는 접수 확인도 끝남으로 표시한다. **상태로 판정하고 시점으로 판정하지 않는다**(켜는 순간 모든 웹접수 건에 「이미 답함」 지문을 심어 미답변 문의가 방치된 사고) — 기준선 id 는 seen 유실 시 이미 답한 건의 이중 답변 방지에만 쓴다. 추가 답변은 앞의 실제 답 블록(hold 답 포함, ⏱ 줄로 판별) 뒤에 「추가 답변」으로 이어 붙인다. 시도 횟수는 내용(지문) 한 벌당 — 새 추가 질문·성공한 답이 0 으로 되돌리고, 같은 내용으로 3회 실패하면 더 부르지 않고 담당자 몫(모든 호출을 누적해 세던 탓에 추가 질문이 조용히 영영 건너뛰어지던 결함). **스크린샷**: 프롬프트에 문의별 그림 파일 경로를 주고 Read 로 열어 확인하게 한다(못 열면 hold·글로 다시 요청) — `claude -p --add-dir <그림 폴더>`. 실측: 무인 호출이 시험 그림 속 글자를 정확히 읽음(권한 거부 0). 담당자 대시보드는 아직 `[[사진:N]]` 을 글자로만 보인다(그림 보기는 제안 단계). 원표봇은 사람이 답한 건에 손대지 않으므로, 그런 건에 부재 중 붙은 추가 질문은 복귀 보고서의 「담당자가 답했던 건에 붙은 추가 질문」으로 담당자에게 알린다. 위임 경계의 정본 = `부재중_에이전트_운영규칙.md` — 코드보다 문서가 먼저. 예외(2026-09-11): 담당자 본인(설정된 성함·소속)이 넣은 시험 문의는 봇이 물은 만큼 다 답하면 감시자가 스스로 완료로 닫는다(비용 0). 현업 화면은 봇 답이 달린 「대기」를 「1차 답변 완료」로 보인다(실제 상태는 그대로).

- R22 **엔진은 갈아 끼울 수 있게, 단 격리를 증명한 엔진만.** 실행 명령·출력 파싱·도구 이름·격리 방식을 어댑터 한 곳(`engines.py`)에 모으고, 설정 한 줄로 엔진을 고른다. 어댑터는 엔진 출력을 **기존과 같은 모양**으로 정규화해 그 아래 파이프라인을 손대지 않는다. 새 엔진은 `probe_isolation.py` 로 **일부러 금지된 일(셸·쓰기)을 시켜 보고 거부되는 것을 흔적으로 확인**한 뒤에만 무인 실행에 쓴다 — 통과해도 사람이 직접 설정을 켜야 한다(자동으로 켜면 확인 스크립트가 틀렸을 때 아무도 모르게 열린다). 리팩토링 제1 제약은 **기존 경로 바이트 동일** — 실행 인자·프롬프트 조립을 골든 스냅샷으로 고정하고 매 단계 대조한다. 규칙 문서는 정본 하나에서 호스트별 파일을 생성하고(손으로 맞추면 반드시 낡는다 — 실측으로 4건 누락 확인), 낡으면 점검 스크립트가 막는다. 답 JSON 은 규격을 정해 모델별 변형을 정규화하되 규격 밖은 버리지 않고 기록한다. 파일 도구는 읽기 전용 MCP 서버로 분리해 엔진이 바뀌어도 제한이 같게 한다.
- R21 **조사 범위에 사내 작업 카드를 추가하되, 공개 답에는 번호·요청자를 절대 내지 않는다.** 아카이브·선례로 결론이 안 나면 관련 작업 카드(키워드 Grep → 경량 인덱스에서 라인범위 확인 → 그 범위만 Read, 카드 전체를 읽지 않는다)를 참고해 **판단 방향에만** 쓴다. 프롬프트가 카드 번호·요청자·내부 추적 번호를 공개 답변에 쓰지 말라고 지시하고, 쓰기 게이트가 정규식(작업카드·문의·SR/변경 번호 패턴)으로 한 번 더 막는다 — 걸리면 조용히 표준 문구로 되돌리고 기록만 남긴다(모델이 지시를 빠뜨릴 수 있는 마지막 관문). 실제 있었던 문의를 재현한 실측 1건에서 카드를 스스로 찾아 방향만 반영하고 번호·이름·서버 정보를 전부 제외한 것을 확인했다.
- R20 **원표봇 권한은 판정으로 늘린다.** 설정 `stages`(단계 · 최소 판정 건수 · 최소 정확도 · 최근 N건 중 최대 틀림 · 맡기는 일)를 장부가 현업 문의 판정(시험 제외)으로 계산해 지금 단계와 다음 단계까지 남은 것을 보여 준다. 승격은 담당자가 정하고 코드를 바꿔 연다. 고위험 영역(금액·여신·결산·되돌릴 수 없는 절차) 틀림 1건이면 한 단계 내린다.
- R19 **원표봇 호출은 격리하고, 한 일을 남긴다.** 헤드리스 호출은 담당자 PC 의 설정을 물려받는다 — 개인 플러그인 훅(도구마다 프로세스가 떠 느린 PC 에서 호출이 15분 제한에 걸림)과 프로젝트 권한 목록의 허용 규칙(원표봇이 셸로 grep·sed·wc 를 실제 실행). 그래서 감시자가 원표봇 전용 설정 파일을 **매 호출 다시 써서** `--settings` 로 넘긴다: `disableAllHooks` + 막는 규칙(Bash · PowerShell · Write · Edit · MultiEdit · NotebookEdit · Agent · Task · 개발계 100 연결 — 웹 검색·페이지 읽기는 2026-09-11 허용: 결론이 안 날 때만 · 호출당 검색 3 · 페이지 2 · 검색어는 행동 로그에서 사내 식별자 점검) — 막는 규칙은 어느 층의 허용보다 우선한다. 행동 로그 = `--output-format stream-json --verbose` 의 도구 사용을 runs/<시각>.stream.jsonl · journal `behavior`(도구 수 · 읽은 파일 · 검색어 · 사진 열람 · 개발계 조회 · 거부된 시도) · 복귀 보고서 「원표봇 행동 기록」(사진 미열람 · 허용 밖 시도 경고). 제어판은 켠 직후 「감시자 켜는 중」, 끊김 판정 90초, 떠 있는 동안 3분 넘게 멈춘 감시자를 스스로 되살린다(10분에 한 번). 호출을 가볍게: 운영 규칙의 원표봇 관련 절(§0 · §2 · §3~§6)을 매 호출 파일에서 잘라 프롬프트에 붙인다(원표봇이 파일을 나눠 읽던 턴 제거 · 제목을 못 찾으면 직접 읽으라고 안내) · `--strict-mcp-config --mcp-config <아카이브>/.mcp.json` 으로 조회 연결 하나만 올린다 · 담당자 개인 설정(전역 CLAUDE.md)과 자동 메모리 색인은 싣지 않는다(`--setting-sources project,local` · `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` — 아카이브 규칙은 그대로) · 쓸 일이 없는 기본 도구는 차단 목록에 넣어 목록에서 뺀다(ToolSearch 는 남김). 비용은 턴 수보다 매 호출 고정 입력의 캐시 쓰기가 좌우한다.
