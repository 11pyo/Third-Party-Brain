# 대시보드 운영 가이드 — 규칙 & 사용법 (사람용)

> `05-operational-layer`가 **"왜 이런 레이어가 필요한가(개념)"**라면, 이 문서는 **"그래서 실제로 어떻게 굴리나(운영 매뉴얼)"**입니다.
> 지식 아카이브(`archive.html`)가 *정리된 지식*을 담는다면, 대시보드는 *지금 진행 중인 일·문의·사람*을 담습니다. 둘은 한 폴더에서 같이 돕니다.
> ▶ **실행 가능한 익명 동작본**: `reference-implementation/dashboard/` — 이 문서가 설명하는 보드가 그대로 도는 샘플(더블클릭 실행, 데이터는 전부 가상).

원본 사례는 1인이 모듈(예: SAP SD) 운영을 맡으면서, 여러 AI 대화 세션이 같은 작업판을 동시에 갱신해도 어긋나지 않게 만든 대시보드입니다. 서버·DB 없이 **파일 몇 개 + 더블클릭**으로 돕니다.

## 1. 구성 파일 11개

| 파일 | 역할 | 누가 쓰나 |
|------|------|----------|
| `tasks.md` | **정본(正本).** 프로젝트 태스크(개발·운영)의 칸반·상세를 마크다운으로. 사람이 읽고 고치는 원본. | 사람·AI 직접 편집 |
| `task-board.html` | **화면.** `tasks.md`를 미러링한 단일 HTML 보드. 더블클릭으로 브라우저에서 열림(서버 불요). | 정본을 보고 미러 갱신 |
| `inquiry-log.js` | **문의 처리이력 데이터.** 추가전용(append-only) 푸시로그. `task-board.html`이 `<script src>`로 읽음. | ⚠️ **직접 편집 금지 — 헬퍼로만** |
| `log-inquiry.py` | **문의 로그 헬퍼.** 한 줄씩 안전하게 덧붙이는 작은 CLI. | 문의 기록/전이/완료 시 호출 |
| `board-saver.py` | **저장 서버(선택).** 켜 두면 화면에서 고친 내용을 저장할 때 **어디에 저장할지 묻지 않고 원본 파일을 그대로 덮어씁니다.** 내 PC에서만 열립니다. | 휴가모드가 켜고 지킴(평소엔 필요할 때 제어판에서) |
| `intake-server.py` | **접수 서버(선택).** 켜 두면 사내 현업이 브라우저로 SD 문의를 직접 등록합니다. 「문의하기」 칸에는 이메일처럼 **글 사이에 스크린샷을 붙여 넣을 수 있고**(커서 자리에 Ctrl+V, 여러 장), 「내 문의함」에서는 **자기가 낸 문의와 답변만** 대화처럼 보고 추가 질문을 이어 달 수 있습니다. 담당자 대시보드는 이 창구로 보이지 않습니다. | 휴가모드가 켜고 지킴(평소엔 필요할 때 제어판에서) |
| `vacation/mode.py` | **부재중 모드(원표봇) 스위치.** 켜면 먼저 어떤 문의가 아직 답을 기다리는지 기준을 잡아 두고, ①두 서버(접수·저장) ②PC 무중단 설정 ③감시자를 차례로 올립니다(켜기 확인창의 3단계와 같습니다). 켜기 전에 들어와 아직 답이 없는 문의도 곧바로 처리합니다. 끄면 PC 설정을 원래대로 돌리고 복귀 보고서를 열어 줍니다(보고서는 AI를 부르지 않아 비용이 들지 않습니다). 두 서버는 끄지 않고 둡니다 — 복귀 직후에도 현업이 답을 볼 수 있게. 보고서에는 AI가 남긴 담당자용 메모와, 담당자가 답했던 문의에 부재 중 붙은 추가 질문 목록도 모입니다. | 제어판 버튼으로 실행 |
| `vacation/watcher.py` | **감시자.** 문의 파일이 바뀌면(45초 기다렸다가) 아직 답이 없는 새 문의에 먼저 「접수 확인」을 달고(이미 답이 달린 문의에는 달지 않습니다 — 앞선 답을 덮지 않게), AI에게 1차 답변 판단을 맡깁니다. 문의에 붙은 스크린샷도 AI가 직접 열어 봅니다. 같은 내용으로 세 번 실패하면 더 부르지 않고 담당자 몫으로 남깁니다(추가 질문이 붙으면 다시 셉니다). 바뀐 게 없으면 AI를 부르지 않으므로 기다리는 동안 비용이 들지 않습니다. 접수·저장 서버가 죽어 있으면 창 없이 되살립니다. | 휴가모드가 띄움(직접 쓰지 않음) |
| `vacation/servers.py` | **서버 켜는 곳.** 휴가모드가 두 서버(접수·저장)를 켤 때, 재부팅 뒤 되살릴 때, 감시자가 꺼진 서버를 되살릴 때 모두 이 파일을 씁니다. 창 없이 떠서 실수로 닫힐 일이 없고, 서버가 남기는 글은 기록 파일로 모입니다. | 휴가모드가 사용 |
| `vacation/ledger.py` | **검증 장부.** 원표봇이 답한 문의와 담당자의 판정(맞음·보완·틀림)을 모아 현업 문의 기준 정확도, 판정을 기다리는 답, 틀린 답에서 무엇이 달랐는지를 한 장으로 정리합니다. 시험 문의는 따로 셉니다. | 제어판 버튼 · 복귀 보고서 |
| `vacation/apply_answer.py` | **쓰기 관문.** AI의 판단을 문의 로그에 기록하는 유일한 통로입니다. 「원표봇 · AI 1차 안내」 표기를 떼지 못하게 붙이고, 상태는 항상 「대기」로 둡니다(닫는 건 사람). AI가 담당자에게 남긴 메모는 답변에 붙이지 않고 기록에만 남겨 복귀 보고서의 「담당자용 메모」로 보여 줍니다(현업에게는 가지 않습니다). 기록한 뒤 다시 읽어 제대로 들어갔는지 확인합니다. | 관문 전용 |
| `vacation/config.json` · `vacation/sysmode.ps1` | **설정 + PC 무중단 스크립트.** 설정 파일엔 기다리는 시간·한 번에 처리할 건수·하루 호출 한도 등이, 스크립트엔 휴가 동안 PC가 절전·자동 업데이트·자동 재부팅으로 꺼지지 않게 하는 설정이 들어 있습니다(바꾸기 전 값을 백업했다가 복귀 때 그대로 되돌림). | 사람(설정) / 휴가모드가 호출 |
| `dashboard-panel.pyw` | **바탕화면 제어판.** 접수 서버·저장 서버와 휴가모드를 버튼으로 켜고 끕니다. 대시보드·현업 화면 링크, 방화벽 상태, 문의 건수도 보여 줍니다. 서버를 PC 켤 때 자동으로 켜는 설정은 없앴습니다 — 두 서버는 휴가모드가 켜고 지킵니다. 방화벽 상태를 확인하지 못하면 「닫힘」이 아니라 마지막으로 확인된 상태를 보여 줍니다. | 사람이 켬 |

> 핵심 분리: **프로젝트 태스크**는 사람이 정본 마크다운(`tasks.md`)으로 관리하고 화면에 미러링, **문의 이력**은 헬퍼가 추가전용 로그(`inquiry-log.js`)에 쌓습니다. 둘의 동기화 방식이 다른 이유는 4·5장에서 설명합니다.

## 2. 세 개의 보드

화면(`task-board.html`)에는 보드가 3종 있습니다.

1. **프로젝트 태스크 보드** — 일회성 작업(개발/운영 건). 상태 4열 **접수 → 진행중 → 대기 → 완료**.
2. **정기업무 보드** — 주례/월례/연례처럼 *트리거가 오면 반복*되는 일. 일회성과 섞이지 않게 **별도 보드**로 둠(평소엔 "지금 할 일 아님" 상태로 대기).
3. **문의 처리이력 보드** — 일반·단순·긴급 문의. 역시 **접수 → 진행중 → 대기 → 완료** 4열. 데이터는 `inquiry-log.js`.

### 카드는 무엇으로 구성되나
- **ID** (예: `DEV-001`, `OPS-002`, 문의는 `INQ-260601-101500`) + **제목**
- **요청자·조직 칩** — 코드 옆에 작게: "누가·어느 조직이 요청했나"를 한눈에
- **기한 / 다음 액션** — 당장 뭘 해야 하는지
- **상세**(접기/펼치기) — 처리 이력·근거·참조 앵커
- **완료 열**은 높이를 고정하고 **스크롤**, 카드는 **최신순**(가장 최근 완료가 위)

**완료 열** 머리에는 **`+전체보기`** 버튼이 있어(완료 카드가 1건 이상일 때), 누르면 완료 카드를 큰 모달로 모아 봅니다(완료가 쌓였을 때 한눈에 보기 좋게).

## 3. 문의 로그의 핵심 — 추가전용 + id 병합 (여러 세션이 동시에 써도 안전)

이게 이 대시보드에서 가장 중요한 패턴입니다. 여러 AI 세션(또는 사람+AI)이 같은 로그를 동시에 갱신해도 충돌이 안 나게:

- **추가만 한다 (append-only)** — `inquiry-log.js`는 한 줄 = 한 이벤트. 기존 줄을 고치지 않고 **새 줄을 덧붙임**.
  ```js
  window.INQUIRY_LOG.push({id:"INQ-...", date:"...", type:"단순문의", q:"문의 요약", by:"기록자", status:"접수"});
  window.INQUIRY_LOG.push({id:"INQ-...", status:"진행중"});          // 같은 id — 상태만 덧붙임
  window.INQUIRY_LOG.push({id:"INQ-...", status:"완료", a:"처리 요약"}); // 같은 id — 답변 채우며 완료
  ```
- **id로 병합한다 (id-merge)** — 화면이 그릴 때 **id별로 줄을 접어(fold) 마지막 값으로 병합**. 그래서 "접수→진행중→완료"라는 *상태 전이*가 파일에선 "기존 줄 수정"이 아니라 **"새 줄 덧붙임"**으로 표현됩니다. (빈 값은 병합에서 무시 → 준 필드만 덮어씀)
- **헬퍼로만 쓴다** — 로그 파일을 직접 손대지 않고 작은 스크립트(`log-inquiry.py`)가 줄을 덧붙입니다. 두 세션이 동시에 덧붙여도 줄이 섞이지 않게, 헬퍼는 **짧은 OS 파일락**으로 덧붙임 구간을 보호합니다(락이 실패해도 기록 자체는 유지하는 best-effort).
- **`file://` 우회** — 브라우저가 로컬 파일을 `fetch` 못 하는 제약을, 데이터를 `<script src="inquiry-log.js">`로 불러오는 방식으로 우회. HTTP 서버가 필요 없습니다.

> 왜 중요한가: **잠금장치나 데이터베이스 없이도, 여러 자율 AI가 같은 작업판을 드리프트(상태 어긋남) 없이 동시 갱신**할 수 있게 됩니다. 일반적인 파일 덮어쓰기 방식이면 한 세션의 기록이 다른 세션 것을 날렸을 겁니다.

## 4. 운영 규칙

대시보드를 만지는 모든 사람·AI가 지키는 규율입니다.

- **R1. 정본은 마크다운, 화면은 미러.** 프로젝트 태스크의 진실은 `tasks.md`. `task-board.html`은 그걸 비추는 화면일 뿐이니, 태스크를 바꾸면 **둘 다** 맞춥니다. (정본↔화면 동기화는 "작업의 일부")
- **R2. 문의 로그는 헬퍼로만.** `inquiry-log.js`를 손으로 편집하지 않습니다. 추가전용 + id 병합이라는 무결성·동시성 보장이 깨지기 때문(세션 제한이 아니라 데이터 안전 때문).
- **R3. 모든 세션이 전권, 충돌은 2규칙으로 막는다.** 이 폴더를 보는 **어느 대화 세션이든 모든 파일을 고칠 권한**이 있습니다(파일 도메인 분리 없음 — 빈 세션 1개가 프로젝트 1개를 끝까지 맡는 모델). 대신 ① **편집 직전 항상 파일을 다시 읽고**(다른 세션이 바꿨을 수 있음) ② **문의 로그만은 헬퍼로** 갱신합니다.
- **R4. 요청자·조직 칩을 채운다.** 문의·태스크엔 "누가·어느 조직이 요청했나"를 칩으로 남겨, 나중에 추적·라우팅이 됩니다.
- **R5. 추가·삭제 시 3곳 동기화.** 태스크를 추가/삭제하면 ① 정본 `tasks.md` ② 화면 `task-board.html` ③ (집계 카운트가 있으면) 합계 숫자를 함께 맞춥니다.
- **R6. 정기업무는 분리해서 트리거 대기.** 월례·연례 업무는 일회성과 섞지 말고 정기 보드에 두되, 평소 상태는 "트리거 대기"로. 트리거(메일·요청 수신)가 오면 그때 착수.
- **R7. 완료는 스크롤·최신순·전체보기.** 완료가 계속 쌓이므로 완료 열은 높이 고정+스크롤, 최신이 위, 한눈에 볼 땐 전체보기 모달.
- **R8. 민감정보는 데이터 파일(로컬)에만, 공개본엔 패턴만.** 실제 `tasks.md`·`inquiry-log.js`엔 고객명·문서번호·금액·담당자명이 들어갑니다 — 이건 **로컬/사내용**입니다. 공개(이 블루프린트 같은)에는 **구조·규칙·익명 예시만**. 전화·이메일·사번 같은 PII는 데이터 파일에도 넣지 않고 비공유 로컬에 따로 둡니다.
- **R9. 저장 서버는 내 PC 전용 통로.** 보드 화면에서 고친 것을 파일로 저장하는 서버(5178)는 **내 컴퓨터에서만** 접속되게 둡니다. 읽기만 하는 아카이브 공유 서버와 성격이 달라 — 사내망에 열면 누구나 파일을 덮어쓸 수 있습니다.
- **R10. 접수 서버는 사내망에 열되, 쓰기는 「신규 등록」과 「본인 문의에 추가 질문」 둘뿐.** 현업이 문의를 넣는 창구(5179)는 열려 있지만 수정·상태변경·삭제 기능은 만들지 않습니다. 스크린샷도 따로 올리는 통로 없이 **이 두 요청에 글과 함께 실려서만** 들어옵니다 — 글은 들어갔는데 그림만 빠지거나 사진 번호가 어긋나는 일을 막기 위해서입니다. 서버 안에서 쓰는 일(신규 등록·추가 질문·사진 정리)은 한 줄로 세워 차례로 처리합니다 — 같은 문의에 추가 질문이 동시에 들어와 사진 번호가 겹치거나, 정리 작업이 막 들어오는 사진을 지우는 일을 막습니다. 거절하는 요청도 끝까지 받아 읽은 뒤 답해서, 현업 화면에 「연결 끊김」이 아니라 진짜 거절 사유가 보이게 합니다. 저장 서버와 절대 합치지 않습니다.
- **R11. 현업 화면에 보이는 것은 세 겹으로 제한.** ①웹으로 직접 접수한 건만 ②성함·소속이 일치하는 본인 것만 ③접수번호·날짜·유형·상태·문의내용·답변, 그리고 이를 대화처럼 보여 주기 위한 정보(대화 순서·추가 질문 횟수·추가 질문 가능 여부·첨부 사진 번호·남은 사진 자리)만. 담당자용 참조·기록자·요청자 원문은 넘기지 않습니다. 사진도 본인 확인을 통과해야 보여 줍니다.
- **R12. 답변 속 내부 메모는 `[[내부]]` 로 감싼다.** 대시보드에는 남고 현업 화면에서만 지워집니다.
- **R13. 기다리는 것에는 기한을 붙인다.** 남의 회신을 기다려 카드를 「대기」에 둘 때는 **무엇을 누구에게 · 보냈는지 · 언제까지**를 카드에 한 줄로 적습니다. 이때 **「보냈는지」의 기본값은 「미확인」** — 본인이 직접 보내고 AI에게 말하지 않을 수 있으니, AI가 「안 보냄」으로 단정하면 안 됩니다. 인덱스 생성기가 이 줄을 모아 「회신 대기」 표로 올리고 기한이 지난 건을 표시하므로, **다음 세션이 오늘 날짜와 비교해 「보내셨나요·회신 왔나요」를 한 번 묻게** 됩니다. 규칙만 있고 확인하는 장치가 없으면, 보내지도 않은 메일을 기다리며 카드가 몇 주씩 멈춥니다(실제로 그랬습니다).
- **R14. 부재중 모드(원표봇)의 AI는 직접 쓰지 않는다.** 담당자가 자리를 비우면 원표봇이 문의에 1차 안내를 달지만, AI 자체에는 읽기 권한만 있고 「답변 / 보류 / 사람에게 넘김 / 개발 검토」 판정만 돌려줍니다(쓰기를 맡겼더니 권한에 막혀 조사만 하고 조용히 멈춘 적이 있습니다). 기록은 쓰기 관문 한 곳만 하며, 관문이 ① 「원표봇 · AI 1차 안내」 표기를 떼지 못하게 붙이고(이름을 붙여도 AI라는 사실은 숨기지 않습니다) ② 상태를 항상 「대기」로 두고(닫는 건 사람) ③ 기록 뒤 다시 읽어 확인합니다. AI가 담당자에게 남기는 메모는 답변에 붙지 않고 복귀 보고서의 「담당자용 메모」로만 갑니다. AI는 문의 파일이 바뀔 때만 불리므로 **기다리는 동안 비용이 0**입니다. 그리고 **켜기 전에 들어와 아직 답이 없는 문의도 곧바로 처리합니다** — 「언제 들어왔나」가 아니라 「물은 만큼 답이 달렸나」로 판단합니다(켜는 순간 이전 문의를 모두 「답한 것」으로 쳤다가 미답변 문의가 2시간 방치된 적이 있습니다). 그래서 AI가 첫 문의에만 답하고 뒤에 붙은 추가 질문이 아직이면 그것도 처리 대상이고, 휴가모드를 켤 때 담당자가 진행중·대기로 옮겨 둔 문의는 가로채지 않습니다(추가 질문이 붙으면 다시 봅니다). 「접수 확인」은 답이 비어 있는 문의에만 달아 앞선 답을 덮지 않고, 추가 답변은 앞의 답(보류 안내 포함) 뒤에 이어 붙입니다. 문의에 붙은 스크린샷은 AI가 직접 열어 보고, 못 열면 보류하거나 글로 다시 부탁합니다(담당자 대시보드에서는 사진 자리가 아직 글자로만 보입니다). 같은 내용으로 세 번 실패하면 더 부르지 않고 담당자에게 남기며, 새 추가 질문이 붙으면 처음부터 다시 셉니다. 원표봇은 담당자가 답한 문의에는 손대지 않으므로, 그런 문의에 붙은 추가 질문은 복귀 보고서에서 따로 알려 줍니다. 무엇을 AI가 처리하고 무엇을 사람에게 넘기는지는 코드보다 먼저 운영규칙 문서에 적어 둡니다. 예외(2026-09-11): 담당자 본인(설정된 성함·소속)이 넣은 시험 문의는 봇이 물은 만큼 다 답하면 감시자가 스스로 완료로 닫는다(비용 0). 현업 화면은 봇 답이 달린 「대기」를 「1차 답변 완료」로 보인다(실제 상태는 그대로).
- **R15. 스크린샷은 공유 폴더 밖에, 번호는 재사용하지 않고, 종결되면 지운다.** 캡처에는 고객명·금액이 찍히므로 공유본(아카이브 폴더) 밖에 문의별로 저장합니다. 파일 이름은 서버가 번호로 짓고, 그림 형식은 확장자가 아니라 파일 내용으로 확인합니다. 한 번 쓴 사진 번호는 다시 쓰지 않습니다 — 종결돼 사진이 지워진 문의에 추가 질문이 붙어도, 옛 글의 「사진 1」이 새 그림을 가리키면 안 되기 때문입니다. 문의가 완료되면 사진 폴더는 자동으로 지워지되(이 정리도 등록·추가 질문과 한 줄로 세워 처리합니다 — R10), 막 들어온 사진은 30분 기다립니다(종결된 문의가 추가 질문으로 다시 열리는 중일 수 있습니다).
- **R16. 화면 스크립트는 배포할 때마다 「문법 검사 + 브라우저로 열어 보기」.** 서버가 파이썬 문자열 안에 화면 스크립트를 담아 내보낼 때는 역슬래시(`\`)를 쓰지 않습니다 — 파이썬이 이를 다른 문자로 바꿔 화면 전체가 반응하지 않게 됩니다. 배포마다 내보내는 스크립트를 문법 검사하고, 실제 브라우저로 열어 **콘솔 오류 0 · 스크립트가 끝까지 실행됐는지**를 봅니다. 대시보드처럼 마지막 화면이 파일에 저장된 페이지는 스크립트가 중간에 멈춰도 옛 화면이 그대로 떠서 멀쩡해 보이기 때문입니다(실제로 문의 보드가 옛 목록에 멈춰 있었습니다).
- **R17. 무인으로 도는 것은 끊겨도 스스로 돌아와야 합니다.** 원표봇 감시자는 창 없이 떠서 실수로 닫힐 일이 없고, PC 가 다시 켜지면 로그인할 때 휴가모드가 켜져 있는 경우에만 저절로 되살아납니다. 그래도 끊겨 있으면 제어판의 「감시 다시 켜기」 한 번이면 됩니다. 휴가모드가 바꿔 둔 업데이트 설정이 되돌아가 있으면 감시자가 다시 맞추고 복귀 보고서에 적습니다. 접수·저장 두 서버도 휴가모드가 맡습니다 — PC 를 켤 때 저절로 켜지지 않고, 휴가모드를 켜면 함께 켜지며, 휴가 중 꺼지면 감시자가 1분 안에 되살립니다. 복귀해도 서버는 끄지 않아 현업이 답을 다시 볼 수 있습니다.
- **R18. 원표봇의 답은 사람이 판정해 쌓습니다.** 복귀 후 원표봇이 답한 카드를 고칠 때 맞음·보완·틀림을 고르면 검증 장부에 쌓이고, 원표봇에게 더 큰 권한을 줄지 판단하는 근거가 됩니다. 판정은 현업 화면에 보이지 않고, 원표봇이 같은 문의를 다시 처리하게 만들지도 않습니다. 원표봇은 스스로 배우지 않으므로, 감시자가 원표봇을 부를 때마다 「틀린 답 · 보완할 답과 그 이유」를 함께 보여 줍니다 — 틀린 것으로 판정된 예전 답은 근거로 쓰지 않고, 아직 판정하지 않은 원표봇 답은 다시 확인한 뒤에만 씁니다.
- **R22. AI 엔진은 갈아 끼울 수 있게 하되, 안전이 확인된 엔진만 씁니다.** 실행 방법·도구 이름·답 형식이 모델마다 다르므로 그 차이를 한 곳에 모아 두고, 설정 한 줄로 바꿉니다. 새 엔진은 「명령 실행·파일 쓰기를 정말 못 하는지」 일부러 시켜 보고 확인한 뒤에야 무인 운영에 들어갑니다. 바꾸는 동안 기존 동작이 달라지지 않도록, 바꾸기 전 상태를 먼저 찍어 두고 매번 대조합니다.
- **R21. 원표봇이 사내 작업 카드도 참고하지만, 세부 번호는 밖으로 내지 않습니다.** 아카이브에 없는 질문이라도 비슷한 사내 검토 이력이 있으면 그 방향만 참고해서 답합니다. 어느 카드를 봤는지, 누가 요청했는지는 담당자에게만 남기고 현업 화면에는 나가지 않습니다 — 문구로 지시하고, 혹시 빠뜨려도 자동으로 한 번 더 걸러냅니다.
- **R20. 원표봇에게 일을 더 맡기는 기준을 표로 정해 둡니다.** 현업 문의 판정이 몇 건 쌓이고 정확도가 얼마 이상이면 다음 단계(예: 단순문의는 스스로 완료)로 넘어갈 수 있는지 장부가 보여 줍니다. 넘길지는 담당자가 정하고, 중요한 영역에서 틀리면 한 단계 내립니다.
- **R19. 원표봇은 정해진 도구만 쓰고, 한 일은 기록으로 남습니다.** 원표봇을 부를 때 이 PC 의 개인 개발 도구 설정은 끄고, 명령 실행 · 파일 쓰기 · 코드를 고칠 수 있는 연결은 막습니다(읽기 · 개발계 조회 · 필요할 때만 쓰는 웹 검색). 웹 검색어는 기록되고, 회사 정보가 섞이면 복귀 보고서가 알려 줍니다. 부를 때마다 읽은 파일 · 찾은 말 · 열어 본 사진 · 거절된 시도가 기록되고, 복귀 보고서에 호출별로 모입니다. 제어판은 켜는 중일 때 「감시자 켜는 중」으로 보이고, 감시가 정말 멈추면 스스로 다시 켭니다(제어판이 떠 있을 때).

## 5. 사용법 (How-to)

### A. 문의 한 건을 처리한다 (접수 → 전이 → 완료)

```bash
# ① 접수 — 문의가 들어오면 즉시 (보드 '접수' 열 맨 위에 뜸)
python log-inquiry.py --new --type 단순문의 --q "<문의 요약>" --by <기록자> --req "<요청자·조직>"
#   → stdout 'NEW id=INQ-YYMMDD-HHMMSS' 의 id 를 기억해 둔다 (이후 전이·완료에 씀)

# ② 상태 전이 — 작업 시작/보류 (같은 id)
python log-inquiry.py --id <그-id> --status 진행중      # 또는 대기

# ③ 완료 — 답변이 끝나면 (같은 id에 처리 요약·참조 채우고 완료로)
python log-inquiry.py --done --id <그-id> --a "<처리·답변 요약>" --ref "#<관련-아티클-앵커>"
```

- 접수와 동시에 답이 끝났으면 ①에서 `--a`(또는 `--status 완료`)까지 주면 바로 완료로 들어갑니다.
- 같은 초에 두 건이 동시에 들어와도 한 카드로 합쳐지지 않습니다. 헬퍼가 파일 잠금을 쥔 채 이미 쓰인 번호인지 보고, 쓰였으면 1초씩 밀어 빈 번호를 씁니다(번호 형식은 그대로 — 화면에 찍힌 id 가 실제 id).
- 유형: `단순문의 | 일반요청 | 긴급문의` · 상태: `접수 | 진행중 | 대기 | 완료`
- 필드: `{id, date, type, q(질의), a(답변), by(기록자), req(요청자·조직), ref(아카이브 앵커), status}`

### B. 프로젝트 태스크를 추가/갱신한다

1. **정본** `tasks.md`에 해당 카드의 상세 섹션(본문 + 🤖 AI 참조 로그)을 추가/수정.
2. **화면** `task-board.html`의 태스크 배열(`const TASKS = [...]`)에 같은 카드를 미러링 — 상태·요청자·기한·다음 액션 같은 카드 메타는 **이 배열을 1순위 출처**로 삼는다.
3. 추가·삭제면 **집계 숫자**도 맞춤(R5).

> **2026-08-25 갱신 — 위 1단계 서술 정정**: 예전엔 여기서 `tasks.md` 상단의 손관리 칸반 요약 표(ID·분류·제목·상태·요청자·기한·다음 액션을 모은 표)에 먼저 행을 적으라고 안내했다. 실제 운영해 보니 이 표가 카드 본문·보드 배열과 함께 **3중 수기입력**이 되면서 가장 먼저 낡는 층으로 확인됐다(카드 본문·보드 배열은 최신 상태로 갱신됐는데 요약 표만 옛 상태로 남아있던 사례). 그래서 이 표는 걷어내는 중이고, 카드 메타의 단일 출처를 화면(`task-board.html`)의 `const TASKS` 배열로 정리했다(위 2단계). 정본(`tasks.md`)이 커져 세션이 한 번에 통째로 읽기 어려워지는 문제에는 **경량 인덱스 생성기**(살아있는 카드 목록 + 카드별 라인범위만 추출)를, 3중 수기입력의 드리프트에는 **자동 대조 점검기**(세 벌을 교차 대조해 불일치만 보고하고 직접 고치지는 않음 — 무엇이 맞는지는 사람이 판단)를 함께 두는 방식이 실사용에서 검증됐다. 상세는 `CHANGELOG.human.md` 2026-08-25 항목 참조.

### C. 화면에서 카드를 손본다 (편집 → 파일에 저장)

- 카드의 ✏️ 수정은 우선 **이 브라우저(localStorage)에만** 담깁니다(정본은 아직 안 바뀜). 그래서 마음 놓고 고칠 수 있습니다.
- 편집바의 **💾 파일에 저장**을 누르면 실제 파일에 기록됩니다. 저장되는 방식은 세 가지 중 되는 것부터:
  1. **저장 서버가 켜져 있으면** — 어디에 저장할지 **묻지 않고 원본 파일을 그 자리에 덮어씁니다**(가장 편함). 서버가 저장 전에 형식·크기를 검사하고 백업을 남깁니다.
  2. **꺼져 있으면** — 브라우저가 저장할 파일을 **처음 한 번만** 묻고, 그 뒤로는 같은 파일에 덮어씁니다(브라우저를 껐다 켜면 한 번 더 확인).
  3. 둘 다 안 되면 — 다운로드로 받아 원본에 덮어씁니다.
- 「변경분 내보내기(JSON)」는 예전 방식(손으로 정본에 옮기기)이라 지금은 잘 쓰지 않습니다.

### D. 새로고침 = 반영

화면은 정적 파일이라, 정본/로그를 고친 뒤 **브라우저 새로고침**하면 반영됩니다(빌드·배포 없음).

## 6. 왜 데이터 파일은 공개하지 않나 (익명화 원칙)

실제 `tasks.md`·`inquiry-log.js`에는 **고객사명·실명·문서번호(주문/계산서)·금액·내부 코드·결재번호**가 그대로 담깁니다 — 이건 일을 하기 위한 로컬/사내 데이터입니다. 그래서:

- **공개하는 것**: 보드 구조, 추가전용 id-병합 로그 패턴, 헬퍼 CLI 설계, 운영 규칙 — 즉 *재현에 필요한 방법론*과 *익명 예시*뿐.
- **공개하지 않는 것**: 실제 데이터 파일 자체, 고객/사람 이름, 문서·금액·결재 번호, 사내 커스텀 코드 세부, 그리고 전화·이메일·사번 같은 PII.
- 공유(LAN·공개)본에 무언가를 올릴 땐 항상 이 경계를 먼저 확인합니다.

## 설계 원칙 (요약)

1. **정적 우선** — 대시보드도 서버 없이 더블클릭. 공유는 파일 복사나 아카이브 검색서버 공유에 얹기.
2. **동시성은 추가전용으로** — 락·DB 대신 "덧붙이고 id로 병합". 손실·충돌 0.
3. **정본↔화면 분리, 동기화는 규율로** — 진실은 마크다운, 화면은 미러.
4. **살아있는 문서는 AI가 유지** — 사람이 매번 갱신하는 게 아니라, 업무 흐름에 규율로 묶어 어느 세션이 와도 같게.
5. **공개 경계는 항상 명시** — 데이터는 로컬, 패턴만 공개.
